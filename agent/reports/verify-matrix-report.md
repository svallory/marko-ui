## Findings — genuine registry bugs (reported, not fixed, per task scope)

### Finding 1 — `lyra` native-select is missing its part files

`packages/registry/styles/lyra/ui/native-select/` contains only `native-select.marko`. Every other style (default, luma, maia, mira, nova, rhea, sera, vega) also ships `native-select-option.marko` and `native-select-optgroup.marko` alongside it. All 3 of lyra's native-select demos (`default`, `disabled`, `groups`) import one or both missing files and are skipped for lyra.

- `packages/registry/styles/lyra/ui/native-select/native-select-option.marko` — missing
- `packages/registry/styles/lyra/ui/native-select/native-select-optgroup.marko` — missing

### Finding 2 — `maia` drawer's `variants.ts` has a malformed JSDoc comment (syntax error)

`packages/registry/styles/maia/ui/drawer/variants.ts:72` contains the substring `after:h-*/after:w-*` inside a `/** ... */` block comment. The `*/` inside that string terminates the comment early, leaving the rest of the prose (lines 72-77) as bare, invalid TypeScript. Vite/oxc fails to parse the file with `[PARSE_ERROR] Unexpected token`.

**Severity note:** this is not merely a broken component — it took down the **entire dev server** on first load. marko-run/Vite's SSR module graph appears to build eagerly across all reachable routes rather than lazily per-request; one unparseable `.ts` file anywhere in that graph poisoned every route, including pre-existing, unrelated pages (`/`, `/docs/components/badge`, etc.) that don't import maia's drawer at all. The verify-matrix generator now pre-parses every registry `.ts` file it's about to reference (via `Bun.Transpiler`, syntax-only, no module resolution) and excludes any component whose files don't parse — this is what let the rest of the 509-route matrix build and the dev server boot at all. `maia/drawer` is excluded from the generated matrix as a result (recorded in `verify/manifest.json`).

- `packages/registry/styles/maia/ui/drawer/variants.ts:72:51` — `after:h-*/after:w-*` closes the block comment early

### Finding 3 — `nova` (and likely `sera`) combobox references an undefined `anchor` variable

`packages/registry/styles/nova/ui/combobox/combobox.marko` (and `packages/registry/styles/sera/ui/combobox/combobox.marko`, same snippet) contains `data-chips=(!!anchor)` where `anchor` is never declared anywhere in the file — a `ReferenceError: anchor is not defined` is thrown client-side. Confirmed via actual browser execution against `nova/combobox`'s demos:

```
ReferenceError: anchor is not defined
    at Object.$if_content__setup [as signal]
    (.../packages/registry/styles/nova/ui/combobox/combobox.marko:77:43)
```

Every `nova/combobox` test run threw this and failed deterministically — this is the one non-flaky, non-baseline failure in the whole suite. `sera/combobox` contains the identical bad line but did not throw in this run's demo set/interaction path (its combobox demos may not exercise the code path that reaches `data-chips`); flagging it as **latent, unconfirmed-triggered**, not yet reproduced by this suite.

- `packages/registry/styles/nova/ui/combobox/combobox.marko:~130` — `data-chips=(!!anchor)`, `anchor` undefined
- `packages/registry/styles/sera/ui/combobox/combobox.marko:~142` — same bad line, not confirmed to trigger in this run

## Known flaky area — overlay open/close snapshot races (test-infra limitation, not a component bug)

~20 of the 509 tests fail on the DOM-structure-snapshot assertion (`toMatchSnapshot`), always on the same family of components: **dialog, drawer, sheet, navigation-menu, popover, menubar, toast, combobox, carousel** — every one a portal/overlay-based Zag machine with its own CSS transition duration. The interaction pass clicks each demo's trigger, waits, presses Escape, and polls `data-state` to leave `"open"` before the section is snapshotted; this reduced failures from 59 → ~20 but did not eliminate them — different runs fail on different members of that overlay family (never a new kind of failure, always the trigger's `data-state`/`aria-expanded` toggled the "wrong" way for the snapshot). This reads as each style's close-transition timing occasionally outlasting the 2s poll, or Escape's keydown occasionally not reaching the currently-focused portal target before the next demo's assertions run.

This was investigated across 4 iterations (raw fixed sleep → `waitFor detached` → `waitForFunction` polling `data-state`) without fully eliminating it; further work would mean either extending the poll timeout substantially per-component or asserting structure before the interaction pass rather than after. Left as a documented limitation rather than chased further. **No interaction-click timeouts were recorded as findings** in any run — every clickable control was reachable and clickable; this is purely a snapshot-timing issue on the closing edge, not evidence of a broken interaction.

## Infra caveats

- The dev server's Vite dependency scan is **global and eager** across all statically-reachable routes, not per-request/lazy — a single broken registry file anywhere in the reachable graph 500s *every* route, including unrelated pre-existing pages. This was hit twice during this task (Findings 1 and 2's precursor) before the generator's file-existence and `.ts`-parse pre-checks were added. Anyone adding new components/styles to the registry should be aware that one bad file can take down the whole docs dev server, not just its own page.
- `apps/docs/src/routes/verify/manifest.json` is **not reachable as an HTTP route** (marko-run doesn't serve arbitrary `.json` from `src/routes`; requesting it returns 404) — this is fine, the test spec reads it directly off disk, as the task allowed ("a .ts/.json consumed by tests via fs").
- Playwright's JSON reporter (`e2e/results.json`) did not reliably write to disk when the run was launched via `nohup ... &` in this environment — pass/fail totals and per-style breakdown in this report were derived from the `list` reporter's text output instead, which was reliable across all 10 runs performed during this task.
- 509 routes compiling on first hit is slow (~50-70s for the very first request, since Vite compiles on demand); the warmup curl pass (all 509 routes, `xargs -P 8`) before each Playwright run kept individual test timeouts (60s) from being hit by cold compiles.
