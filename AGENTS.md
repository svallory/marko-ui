# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

marko-ui — "shadcn for Marko": a shadcn-format component registry ported to Marko 6, powered by Zag.js v1 state machines. Bun workspace with three packages:

- `packages/marko-ui` (npm name `marko-ui`) — the published CLI: install and manage Marko UI components from shadcn-format registries (`init`, `add`, `diff`, `show`, `search`, `doctor`, `manifest`, `registry`). Builds with tsup and publishes `dist/` only (`files: ["dist"]`; `exports`/`bin` point at `./dist/...`), so consumers just run `bunx marko-ui init` — no bundler of their own required.
- `packages/shadcn` (npm name `@marko-ui/shadcn`) — component source in shadcn registry format. `ui/<component>/<part>.marko` is the single authored source, tracking shadcn's `new-york-v4` and carrying semantic `mu-*` hook classes; `styles/style-<name>.css` vendors the 8 shadcn style token layers (rhea, nova, vega, lyra, maia, mira, luma, sera) as SOURCE — the package ships source, not precompiled CSS, so import-path consumers add it to their own Tailwind `@source` and compile the `@apply`-based style layers themselves. Per-style flat components (the copy-path artifact `marko-ui add` fetches) are produced IN MEMORY during the registry build by a data swap, not a text rewrite: each component's `classes.ts` (pure data, one export per part) is resolved against the style's CSS by `tooling/resolve-classes.ts`, and `tooling/merge-classes.ts` inlines the resolved literal into the single copy-path file in place of its `./classes.ts` import — there is no on-disk `styles-gen/`. Class strings never live in `.marko`/`variants.ts`; `tooling/check-classes.ts` enforces it as a CI gate.
- `apps/docs` — the docs site (`@marko/run` + Vite + Tailwind v4), which is also the test target for behavior tests.
- `tooling/` — build + check scripts (`build-registry.ts`, `check-*.ts`, `resolve-classes.ts`, `merge-classes.ts`, etc.), run directly with `bun tooling/<script>.ts`. No package.json.

## Commands

Bun only — never npm. Run from the workspace root unless noted.

```bash
bun install
bun run check                  # typecheck all packages + tooling/ + the check-*.ts invariant scripts
bun run test                   # vitest run (all packages/**/*.test.ts)
bunx vitest run packages/shadcn/tests/behavior/tabs.test.ts   # single test file
bun run build:registry         # emit shadcn-CLI-compatible r/*.json
bun run extract:api            # component API extraction
bun run build:demos            # docs demos manifest
bun run build:blocks-manifest  # docs blocks manifest
cd apps/docs && bun run dev    # docs site, default port 3000
```

**Typechecking uses `@marko/type-check`, not `tsc`.** `tsc` cannot parse `.marko` at all, so any `tsc --noEmit` run over this repo silently checks only the `.ts` files and reports success while every component goes unchecked. Each package's `check` script therefore runs:

```bash
NODE_OPTIONS="--max-old-space-size=8192" marko-type-check -p . -d condensed
```

**The repo runs on `typescript` ^6.0.3, the classic JS compiler API** (`ts.createProgram`, `ts.CompilerHost`, `ts.SyntaxKind`/`ts.SymbolFlags`, etc. — all present, unlike TS 7's native `tsgo`, which ships none of it). `tooling/extract-api.ts` builds a virtual `ts.CompilerHost` over in-memory `.ts` twins carved out of each `.marko` file's TypeScript region and hands the whole set to one `ts.createProgram` — no disk writes, no generated tsconfig, no Node/Bun re-exec shim needed; `bun tooling/extract-api.ts` runs directly. Read that file before writing new compiler-API tooling.

**`@marko/type-check` bundles its own typescript (6.0.3), matching the root now** — `marko-type-check` behaviour and error counts have always been independent of the root `typescript` version, and now the majors agree too.

**Do not bump the root `typescript` to ^7.** marko's tooling (`tooling/extract-api.ts`) needs the classic JS compiler API that TS 7 (native `tsgo`) does not ship, and `packages/marko-ui`'s tsup build breaks under TS 7 too, for a different reason — see `packages/marko-ui`'s `typescript` divergence entry in `tooling/check-dep-sync.ts`. If TS 7 is ever revisited, both of those need re-verification, not just the version bump.

**The gate now covers components.** `packages/shadcn/tsconfig.json`'s `include` carries `"ui/**/*.marko"` permanently (landed 2026-08-19), so the type gate covers every component — and the **`packages/shadcn` project is green: 0 errors** as of marko-zag `^1.2.0` (whose `PropTypes` maps all of Marko's native tags; earlier adapter versions collapsed prop getters to `any`, which is why components were never meaningfully checked before). Keep it green: fix type errors properly rather than casting, widening, or `@ts-ignore`-ing them, and treat a new error as a defect in the change that introduced it. A type error at a spread site usually means a real element mismatch — that class of check caught label props on a `<div>` and div-declared components rendering `<span>`/`<a>` the day the gate landed.

**`normalize-mtc.ts` must fingerprint every diagnostic record `@marko/type-check` emits, not just the ones with a `path:line:col - error TSnnnn` header — a gap here silently disarms the whole gate (found 2026-09-15, corrected 2026-09-16, branch `chore/docs-type-cleanup`, PR #36).** `@marko/type-check`'s `main()` prints one `console.log(report.out.join(doubleNewline))`, so raw condensed output is a sequence of blank-line-delimited records. Each record is produced by `reportDiagnostic` in one of exactly 2 shapes (verified against `cli.js` source): (1) `diag.file` set — a `path[:line:col] - <category> TSnnnn` header line followed by the message (`:line:col` present only when `diag.start` is defined; a whole-file diagnostic, e.g. some Marko parse failures, omits it); (2) `diag.file` undefined — the record IS the flattened message text, verbatim, with **no path, no `-`, no category, no `TSnnnn` at all** (real examples: `Cannot read file '...'.` TS5083, `File '...' not found.` TS6053, `No inputs were found in config file ...` TS18003). An earlier fix (2026-09-15) misdescribed shape 2 as "bare `error TSnnnn`, no file" and matched a `(no file)` case in the header regex expecting that text — that regex could never match a real file-less record (there is no `error TSnnnn` substring in one), so the `(no file)` branch was dead code and file-less errors still vanished silently at exit 0, just as before; a PR #36 review caught it empirically (all three real TS5083/TS6053/TS18003 messages produced no fingerprint). Corrected: the normalizer no longer tries to regex-match file-less records at all — any record whose first line doesn't match the shape-1 header format is treated as a file-less diagnostic and fingerprinted directly as `(no file)|TS0000|<first 80 chars>` (deliberately over-inclusive: a stray non-error record with no header would also fingerprint this way, which is the safe failure direction). A `--count` mode reports `<rawRecordCount> <accountedRecordCount>` (every record classified, whether fingerprinted as an error or recognized-and-skipped as a non-error category); `check.sh`/`generate-mtc-baseline.sh` both fail loud on any mismatch between the two, independent of baseline size — this is what actually catches a future regression in the classification logic, not the fingerprint output itself.

**A `(no file)|TS0000|{"type":"message","message":"Detected an AI agent environment..."}` "NEW error" is NOT a repo defect — it is a proto shim writing NDJSON into mtc's stdout (root-caused 2026-09-17).** On a machine where `bun` resolves through `~/.proto/shims/bun`, proto detects an agent environment (the `AI_AGENT` env var, set by Claude Code and similar tools) and prints a JSON banner on **stdout**. Nested `bun run --filter` invocations inherit it, so the banner lands inside `marko-type-check`'s captured output, and `normalize-mtc.ts` — correctly, per the over-inclusive shape-2 rule above — fingerprints the unrecognised record as a file-less diagnostic. The gate then fails with a "NEW error" that exists nowhere in the source. It cost three review rounds on PR #42 before anyone traced it, having been misattributed to bun itself twice.

Tells that it is this and not a real error: the fingerprint text is literal JSON containing `Detected an AI agent environment`; `bun run check` fails while `cd apps/docs && bash scripts/check.sh` run on its own exits 0 on the *same* tree; and it reproduces identically on a clean `main`. Confirm with `env -u AI_AGENT bun run check`, which exits 0 — that is the diagnostic, and running the gate that way is the workaround. **It does not occur in CI**, where nothing sets `AI_AGENT` and `bun` is not a proto shim. Do not "fix" it by loosening `normalize-mtc.ts`: the over-inclusive branch is deliberate and is what keeps genuine file-less diagnostics (TS5083/TS6053/TS18003) from vanishing at exit 0.

**Operationally: in an agent environment with `AI_AGENT` set, assume `bun run check` can exit 1 on the banner, and run it as `env -u AI_AGENT bun run check`.** Use that form by default when reporting a gate result from an agent session — it costs nothing when the banner is absent and removes the only variable that produces a phantom failure.

Whether the banner actually appears is **environment-dependent, so neither outcome proves anything about the tree**. It reproduced for a PR #44 reviewer while the same commit exited 0 with `AI_AGENT` still set on the author's machine (proto 0.60.2, `bun` 1.3.11 via `~/.proto/shims/bun`, banner absent from captured output even in nested `bun run --filter` invocations). The likely variable is the proto version or shim configuration, not the repo. Practical consequence: **a green `bun run check` from a machine where the banner does not appear is not evidence that someone else's banner failure is invalid, and vice versa** — settle it with `env -u AI_AGENT bun run check` on the machine that saw the failure, and judge the tree by that.

**The mtc gate scripts have their own test coverage (2026-09-16, branch `test/mtc-gate-scripts`), added after PR #36's review found a new hole in each of 3 successive rounds.** `apps/docs/scripts/__tests__/normalize-mtc.test.ts` unit-tests `normalize-mtc.ts` directly (shape-1/shape-2 fingerprinting, dedup `xN`, 80-char truncation, `--count` accounting, a path containing `` - ``, a multi-line message body that itself contains `error TS` text not being mistaken for a new header). `apps/docs/scripts/__tests__/check-gate.test.ts` behavior-tests `check.sh` and `generate-mtc-baseline.sh` end to end, against a throwaway sandbox directory containing unmodified copies of the real scripts plus a stub `marko-type-check` placed first on `PATH` (never runs the real, heap-heavy mtc) — new error vs. baseline, baseline entry gone, mtc crash (non-0/1 exit), normalizer crash, `--count` mismatch, `--force` on baseline regen. The stub hook is `NORMALIZE_MTC_CMD` (defaults to `bun scripts/normalize-mtc.ts`, overridable so a test can point it at a broken stub); `marko-type-check` itself is stubbed via a `PATH`-shadowing directory, no script change needed for that one. Both files run under the root `vitest.config.ts`, whose `include` was widened from `packages/**/*.test.ts` to also cover `apps/docs/scripts/**/*.test.ts` — run with `bun run test:docs` (root) or `bunx vitest run apps/docs/scripts/__tests__/` directly; already covered by CI's `tests` job, which runs `bunx vitest run` against the same root config. Writing these tests surfaced a real, latent bug (not live on `main` — see next paragraph): **fixed 2026-09-16, `fix(docs): stop check.sh dying on an empty-fingerprint baseline`.**

**`check.sh` line `baseline="$(grep -v '^#' mtc-baseline.txt | sed '/^$/d')"` had a LATENT bug — not live on `main` — that would silently kill the whole gate on a baseline with no trailing blank line.** Under `set -euo pipefail`, `pipefail` fails a pipeline if *any* stage exits nonzero, not just the last. `grep -v` exits 1 when it matches nothing; `sed` downstream exits 0 regardless, so pipefail still kills the script at that line before any baseline comparison runs, before either the "no new errors" or "NEW errors" message ever prints. This is reachable on a baseline file containing only comment lines with *no* blank line for `grep -v` to still match (a hand-trimmed file, say) — but `generate-mtc-baseline.sh` (the only thing that writes `mtc-baseline.txt`) always ends its output with `echo` then `printf '%s\n' "$fingerprint"`, leaving trailing blank lines even when `$fingerprint` is empty, and `grep -v '^#'` matches those blank lines and exits 0. Confirmed: real `main`'s `mtc-baseline.txt` (0 known errors) ends in two blank lines, and the pre-fix line reaches its next statement fine against it — the bug never fired in practice, only in an isolated repro built with a file that had no such trailing blank line. Fixed anyway with `|| true` on that assignment (removes the landmine for any future baseline shape, and matches the pattern already used elsewhere in both scripts for command substitutions that legitimately return "nothing found"). `generate-mtc-baseline.sh`'s structurally similar `[ -n "$(grep -v '^#' mtc-baseline.txt | sed '/^$/d')" ]` (line ~72) does **not** have this bug, for a different reason than "argument to `[`" — `set -e` (and pipefail's interaction with it) is suspended for the entire condition of an `if`/`while`/`&&`/`||`, so a failing command substitution inside that condition never trips the shell's exit-on-error at all; verified in isolation, left as-is.

**docs mtc: known limitation — marko-type-check ignores tsconfig `exclude` for `.marko` files, so SITE/DEMOS cannot be split into separate mtc projects.** A 2026-09-12 attempt (branch `chore/split-docs-check`) tried giving `apps/docs` two tsconfigs — a fast SITE project excluding `src/demos/**` for a clean 0-error gate, and a DEMOS project covering just the demos with a known-baseline count. It failed empirically, not for lack of the right glob: excluding `src/demos/**/*` while the then-existing `src/tags/docs/demo-renderer.marko` (a real, necessarily-generated file — see the dynamic-tag hydration-crash note above for why it must use static per-demo imports, not a dynamic `<${tag}/>` lookup; since replaced by the per-component `src/tags/docs/demo-renderers/<name>.marko` tags, branch `feat/docs-component-routes`) still statically imports all ~700 demo `.marko` files made the count **worse** (1185 vs. the 392-error unsplit baseline at the time), because TS composite mode fires TS6307 ("File X is not listed within the file list of project") for every excluded file reached through an included file's import — the same TS6307 class already documented above, just triggered deliberately this time instead of by an `include` gap. Narrowing the exclude and also excluding `demo-renderer.marko` itself did not fix it either: `demo-renderer.marko` kept contributing the bulk of the TS6307s (662 of them) even after every textual reference to it — including its only consumer, `component-preview.marko` — was also excluded, meaning marko-type-check loaded and checked a `.marko` file with zero live reachable import path from any included root. This means `exclude` cannot be trusted to stop marko-type-check from loading a `.marko` file at all; it only reliably suppresses *reporting* for files that have no import edges into or out of the excluded set in the first place. Don't retry this split without first getting a real answer from `@marko/language-tools`/marko-type-check about how (or whether) its project loading can be scoped — the baseline-diff gate above is the accepted workaround, not a placeholder for one.

**The attr-tag codegen mismatch is only PARTIALLY fixable from this repo (2026-09-11, branch `fix/attr-tag-content`).** Per markojs.com/docs/reference/language, an attr-tag's runtime VALUE is always an object shaped `{ content: Body<Args>, [Symbol.iterator] }` — never the bare `Body<Args>` a component author naively writes. For a **parameterized** attr-tag (consumer writes `<@trigger|props|>...</@trigger>`), the component-side type must be `Marko.AttrTag<{ content: Marko.Body<[Args]> }>`, and every invocation must unwrap it: `<${input.trigger.content}(args)/>` (add `?.` before `.content` if the field is optional and invoked unconditionally, or a real TS18048 opens). This form was already correct in `menubar/submenu.marko`, `dropdown-menu/submenu.marko`, `context-menu/submenu.marko` before this fix, and was applied to 13 more parameterized fields that were still wrong: `trigger` in accordion-adjacent `alert-dialog`, `collapsible`, `dialog`, `drawer`, `dropdown-menu`, `editable`, `floating-panel`, `hover-card`, `menubar/menu`, `popover`, `sheet`, `tooltip`, `tour`, plus `chart/line.marko`'s `dotContent`, `chart/pie.marko`'s `centerLabel`/`sliceLabel`, and `sidebar/provider.marko`'s `sidebar`/`main`. Verified: `packages/shadcn` mtc stayed 0 errors before and after; the fixed fields' own demos (tooltip, chart, sidebar) type-check clean where they previously threw TS2353/TS7006/TS2322 at the `<@name|params|>` consumer site.

**A parameterless attr-tag (`<@title>text</@title>`) takes the SAME `Marko.AttrTag<{ content: Marko.Body }>` fix as a parameterized one — the earlier claim that it must stay bare `Marko.Body` was WRONG and is corrected here (2026-09-13, branch `fix/attr-tag-declarations`).** An attr-tag's value is always an object `{ content, [Symbol.iterator] }`, whatever its parameter list; `|params|` only changes `Body`'s argument tuple. The rule is that the declared body key must match the API the component compiles to, and **that key is decided by the component's directory**: a `tags/`-API component (everything in `packages/shadcn/ui/**`, verified by extracting `__marko_internal_api`) needs `content`, while a `components/`-API (class) component needs `renderBody`. Declaring a field bare `Marko.Body` while consumers write `<@field>` is a genuine mis-declaration, and the TS2353 `'["content"]' does not exist in type 'Body<[], void>'` it produces is a CORRECT diagnostic, not an upstream bug. Applied to all 17 such fields — `alert-dialog` `title`/`description`/`media`, `dialog`/`drawer`/`sheet` `title`/`description`/`footer`, `avatar` `badge`, `floating-panel` `title`, `qr-code` `overlay`, `color-picker` `label`, `steps` `completedContent` — plus `apps/docs`'s own `src/tags/create/picker.marko` and `src/tags/typeset/picker.marko` (`trigger`). Each component's read becomes `input.<field>.content` (`?.content` where the field is optional and rendered unguarded). Result: docs TS2353 **99 -> 5** (the 5 left are unrelated: `isActive`, a `"class"` attr on an attr-tag, `animationDuration`), `packages/shadcn` stayed **0 errors**. Fields genuinely passed as plain attributes (e.g. `floating-panel`'s `content`/`actions`, the inner `content` of an already-wrapped `AttrTag<{...}>`) stay bare `Marko.Body`.

**Native-attribute collision: a declared `Input` member must SHADOW the native attribute of the same name — this is ordinary TypeScript, NOT a `@marko/language-tools` bug** (root-caused 2026-09-13, branch `fix/native-attr-omit`; general fix landed as marko-zag 2.1.0's 3rd type param 2026-09-14; **superseded 2026-09-15 by marko-zag 3.0.0**, which makes shadowing automatic and removes the 3rd param entirely). A component whose `Input` intersects native element attributes (every `MachineInput<"div", ...>` here) and then declares a member colliding with one of them gets the two **intersected** under the old (pre-3.0) `MachineInput`, because `&` in TypeScript intersects rather than overrides. `title` on a div is `string | false | null` (`marko/tags-html.d.ts`, `HTMLAttributes.title?: AttrString`), so `MachineInput<"div", P> & { title?: Marko.AttrTag<{ content: Marko.Body }> }` makes `Input["title"]` an unsatisfiable `(string | false | null) & { content: Body } & { [Symbol.iterator]... }`, and every `<@title>` consumer throws **TS2322**. Reproducible in plain `tsc` with no Marko codegen involved, and name-specific: an identically-declared `heading` is clean. An earlier version of this doc blamed `@marko/language-tools` for this — that was wrong on attribution.

**Current pattern (marko-zag ^3.0.0): `MachineInput<Tag, Props>` shadows automatically — every member of `Props` wins over a same-named native attribute, with no 3rd type param and no `Omit` gymnastics.** A component with a colliding member folds it into the `Props` argument via intersection:

```ts
type Extras = { title?: Marko.AttrTag<{ content: Marko.Body }> };
export type Input = MachineInput<"div", dialogMachine.Props & Extras>;
```

The local type name for the folded-in extras can be called anything (`Own`, `Extras` — this repo keeps `Own` for continuity with the retired pattern below); the only thing that matters is that it's intersected into the *second* argument, not passed separately. There is no case where intersecting a declared member with a native attribute *outside* `Props` is wanted — it only produces unsatisfiable (`title`) or lossy (see checkbox below) types.

**Two prior forms of this fix are BOTH retired — do not write either in new code, and prefer migrating one away when touching a component that still has it (mechanical simplification, no type change if done correctly):**
1. The original hand-written `Omit<MachineInput<Tag, Props>, keyof Own> & Own` (predates marko-zag 2.1.0).
2. The 3-param `MachineInput<Tag, Props, Own>` (marko-zag 2.1.0–2.1.x only; that param no longer exists on 3.0.0 — passing it is now a plain TS error, "Expected 2 type arguments, got 3").

`command.marko` keeps its own distinct `Omit<MachineInput<...>, "collection" | "value" | "inputValue">` shape — that one drops machine-owned props entirely rather than shadowing a same-named extra, so it is not an instance of this class and was left as-is across every round of this migration.

**A shadowed prop must never be forwarded to the native element it shadows — it's machine-owned state, not a pass-through attribute.** Two real instances, found migrating to 3.0.0 (2026-09-15): `checkbox.marko`'s hidden-input construction spread `checked: CheckedState` (`boolean | "indeterminate"`) into a return annotated `Marko.NativeTags["input"]["input"]`, whose native `checked` is `AttrBoolean` — `"indeterminate"` doesn't fit. Fix: add `"checked"` to the existing `stripOwnProps` key list at that call site; `api().getHiddenInputProps()` (spread right after) already emits the correct native `checked`, so the stripped value was being overwritten anyway. Two docs demos passed a bare string to `Slider`'s `aria-label` (`@zag-js/slider` types it `string[]`, one label per thumb) — fix: wrap in an array, `aria-label=["…"]`. Under the pre-3.0 intersection bug both of these were silently wrong in different ways: `checked` collapsed to plain `boolean` (lossy — `"indeterminate"` silently accepted a value it couldn't represent), and `aria-label` produced an unsatisfiable type that rejected every possible value including the correct array form, which is why the array form had never been tried. **On any future upgrade of a `MachineInput`-typed component, grep for members that are spread onto a native element (`stripOwnProps`, `...input`, `...api().get*Props()` collisions) — 3.0.0's correct shadowing will surface any such case as a real, fixable type error, not a marko-zag defect.**

Applied to the four `title`-declaring components (`alert-dialog`, `dialog`, `drawer`, `sheet`) first (2026-09-13, hand-written `Omit` form): docs raw **298 -> 247**, baseline **246 -> 201** fingerprints (45 resolved). The `content` collisions on `carousel`/`marquee`/`steps`/`tabs` were fixed 2026-09-14 (3-param form): baseline **201 -> 171** (30 resolved). The 3-param form on all 8 of those components was migrated again to the 3.0.0 `Props & Extras` form 2026-09-15, together with the two `checked`/`aria-label` consumer fixes above: baseline **171 -> 157** (14 resolved: 9 slider `aria-label` unsatisfiable-intersection fingerprints genuinely fixed by the array — 8 `slider/slider-*` demos plus `field/field-slider`, 2 bare-string `aria-label` demos fixed by the array wrap — `message-scroller-previous-context` and `preview-page-2/cards/ui-elements`, 2 checkbox `boolean | "indeterminate"` demos now legitimately accepted — `documents-table` and `notification-settings`, 1 `checkbox-indeterminate` string→boolean variant), `packages/shadcn` stayed **0** throughout, zero new errors at every step. `packages/shadcn` mtc staying 0 was never sufficient evidence this class of bug was fixed — the collision surfaces at **consumer** call sites (`apps/docs`), not inside the component file itself; always check the docs baseline-diff gate too. The `value`-on-`field`/`message-scroller` collision this doc previously predicted did not exist on inspection — neither component declares a `value` member that shadows a native attribute — so nothing needed fixing there.

**Baseline fingerprint gotcha: the key is the first 80 chars of the error message (`apps/docs/scripts/normalize-mtc.ts:30`), so a *narrowed* target type on an unchanged call site shows up as "1 removed + 1 added" instead of a clean diff.** Observed migrating the two `aria-label` slider demos above: under the old intersection bug the message read `Type 'string' is not assignable to type '(string & string[]) | (false & string[]) | ...'` (unsatisfiable, >80 chars before the distinguishing part); under 3.0.0's correct `string[]` target it reads `Type 'string' is not assignable to type 'string[]'` (short). Same file, same line, same underlying bug, but the shortened message no longer matches the old fingerprint's first-80-chars key, so a gate run mid-migration printed it as one baseline entry disappearing and one "new" entry appearing at the same site (a transient artifact of that one run, not a lasting property of the final 157-entry baseline above). When a gate run reports a "new" error, check whether its file:line already had a *different-shaped* baseline entry before concluding it's a regression — it may just be a message-length artifact of a type getting narrower.

**Trap: `marko-type-check` REWRITES the `.marko` sources it checks unless `noEmit` is set.** Run against a tsconfig without `"noEmit": true` it performs declaration emit, stripping each file's `export interface Input` out into a generated `.d.marko` sidecar. A fixture harness that reuses a directory across runs will therefore "pass" on the second run only because the declaration under test was deleted — a false green that looks exactly like a fix. Any scratch mtc harness must set `noEmit`, create each case in a pristine directory, and assert the declaration survived the run before trusting a PASS.

So "the gate is green" is a claim about `packages/shadcn` alone. When judging whether a change regressed types, compare the **same scope** before and after against `main` — a raw root-command total is dominated by pre-existing errors and will hide a one-error regression.

**Delete `tsconfig.tsbuildinfo` before trusting a count.** `marko-type-check` forces `composite`/`declaration`/`incremental` on every project (so declaration-emit diagnostics such as TS2742/TS2883 "cannot be named without a reference to ... This is likely not portable" are in scope for the gate) and writes a gitignored `<package>/tsconfig.tsbuildinfo`. Those emit-time diagnostics are only produced for files the builder decides to re-emit, and a change in `node_modules` resolution does not bump any source file's version — so after a dependency change a stale buildinfo can report **0** on a project that genuinely has 55 TS2883 errors (observed 2026-08-28), and the reverse. The `check` scripts do not clear it; `rm packages/*/tsconfig.tsbuildinfo apps/docs/tsconfig.tsbuildinfo` first whenever the dependency tree changed or two runs disagree.

**TS2883 "cannot be named without a reference to 'PropTypes' from '.bun/@zag-js+types@…'" on every `<zag>` component means `@zag-js/types` is not declared where the components live.** Every `<zag>` api getter (hoisted, and returned via `<return=api/>`) is `ZagApi<M> = ReturnType<M["connect"]>`, i.e. `<Machine>Api<PropTypes>`, so the template's declaration must name `PropTypes` from `@zag-js/types`. TS can only print a bare `@zag-js/types` specifier for a file it has seen resolved through a `node_modules` that is an ancestor of the component; under bun's isolated layout the machine packages reach `@zag-js/types` through their own `.bun/@zag-js+<machine>@…/node_modules/` links, which are not ancestors of `ui/`, so without a project-level resolution TS falls back to the `.bun/…` realpath and reports it as non-portable — 55 files at once, one error each (observed 2026-08-28 after the `<zag>` migration; a stale buildinfo had hidden it). The fix is a real dependency, not an annotation: `packages/shadcn/package.json` declares `"@zag-js/types": "1.43.0"` (it *is* a type-level dependency of every component's public type). Keep it declared; a single `import type { PropTypes } from "@zag-js/types"` anywhere in the project also makes all 55 disappear, which is how to recognise this class of error if it ever returns. Annotating a component's `Input` does nothing — the unnameable symbol is in the api/return position.

**TS2589 ("excessively deep") at a `<const>` that spreads native attributes:** annotate the closure with the tag's *exact* input type, `Marko.NativeTags["<tag>"]["input"]` (e.g. `(): Marko.NativeTags["input"]["input"] => ({ ...stripOwnProps(...), ...api().getHiddenInputProps() })`, see `ui/checkbox/checkbox.marko`). A narrowed `Marko.HTMLAttributes<HTMLInputElement>` is a *different* type, and the structural comparison between it and the native tag's input blows the instantiation depth; removing the annotation instead re-opens TS2883 above. There is no longer a "known 1 error" exception: `packages/shadcn` is 0 errors.

The `NODE_OPTIONS` heap bump is **required** — at the default heap size `marko-type-check` OOMs on this repo with a V8 stack dump. It is baked into each package script, so `bun run check` works without extra setup; keep it there if you edit those scripts. `tooling/` stays on plain `tsc` because it is pure `.ts` (no `.marko` files), where `marko-type-check` would add nothing.

Behavior tests (`packages/shadcn/tests/behavior/`) drive real Playwright against a **running docs dev server** — start `apps/docs` first, and pass `DOCS_BASE_URL` if it isn't on port 3000.

**Always start the dev server on an explicit port and pass `DOCS_BASE_URL`.** Port 3000 on the maintainer's machine is held by an unrelated app that answers HTTP 200 on every path with zero `section[data-demo]` elements; behavior tests default to `http://localhost:3000`, so a stale listener there produces mass failures that look like component regressions but are not. Verify with `curl -s localhost:3000 | grep -o '<title>[^<]*'` before trusting any run.

**Some interaction bugs reproduce only against a PRODUCTION build.** Minified-bundle failures can differ from the dev server's unminified single-instance path, which can hide them. The recipe that reproduces a production-only regression locally:

```bash
cd apps/docs && bun run build                       # prod bundle
PORT=4400 node dist/index.mjs &                     # explicit port, never 3000
DOCS_BASE_URL=http://localhost:4400 bunx vitest run packages/shadcn/tests/behavior/dropdown-menu.test.ts packages/shadcn/tests/behavior/menubar.test.ts
```

A prod build serves instantly (no cold-compile wait). To map a minified frame such as `TypeError: e._.j is not a function` back to source, add `build: { minify: false }` to `apps/docs/vite.config.ts`, rebuild, and read the real identifiers (`$scope._.j`, `closureSignal`, `_closure_get`) — then **revert the config**; it is a diagnostic, not a committed setting.

**Never read a parent component's `api()` from inside a child's attr-tag body.** An `<@trigger>`/attr-tag body is owned by the PARENT's template, so an `api()` written there compiles to a raw scope walk (`$scope._._._._._.<slot>()`) plus a `subscribeToScopeSet` on the parent's api signal. When the child mounts, that notify makes Marko's `_closure` re-queue the subscribed child scopes, and the parent's `<const/api=() => connect(...)>` slot is not assigned on that pass — the walk hits an empty slot and throws `TypeError: $scope._.<slot> is not a function` (a mangled `e._.j` / `e._.l` / `e._.k` in a minified build; the letter is just the parent's api slot). The parent's `<const/api>` is assigned only on the **resume** segment, and a popover/menu opened after hydration renders its portal body client-side only, so on that path the slot is never populated at all. This bit dropdown-menu, menubar and context-menu simultaneously (fixed 2026-08-30): the crash count matches the mounted-submenu count exactly, 1:1.

The fix is to route the parent api through **tag input** as a closure (`parentApi=() => api()`) and let the child compute the merged props in its own `<const>`, handing the caller's body a finished plain object. Closures written in a template are the only serializable currency across a tag boundary — the same rule the SSR-safe Zag pattern already states for services.

A component whose trigger is not a `button`/`[role=button]` needs manual verification of its interaction paths — context-menu (a plain `<div>` trigger opened by `contextmenu`) once carried the identical parent-api crash above while its automated coverage stayed green, because nothing dispatched a `contextmenu` event. Don't assume a passing automated suite covers non-click trigger paths; verify those by hand.

**Marko 6.3.46 terminates an HTML comment (`<!-- ... -->`) at the first bare `->`, not at the real `-->`.** Any comment body containing an ASCII arrow in prose — e.g. "so the page read h1 -> h3" — truncates the comment right there; everything after that `->` up to the next `-->` (or end of file) is emitted as literal page text instead of staying hidden. Verified with `compileSync` on the real file, both `optimize: true/false` and `output: "html"/"dom"` — identical behavior, so it is not a minification or hydration-mode artifact. This shipped once, in `routes/docs/components/$name/+page.marko`'s hero-heading comment, and leaked ~730 characters of internal commentary onto every component docs page in production (fixed 2026-09-17 — the arrow became "to"). `bun tooling/check-html-comments.ts` (wired into `check:tooling`) now fails the build on any `.marko` HTML comment containing a bare `->` before its closing `-->`. When writing a code comment that needs to express a range or transition (`h1 -> h3`, `A -> B`), spell it out ("to") or use a real Unicode arrow (`→`) instead of the ASCII `->` digraph.

`packages/marko-ui/tests/` (the CLI unit suite) needs no server. `packages/shadcn/tests/hydration-invariant.test.ts` DOES — despite the "SSR" in its name it captures SSR markup with a JavaScript-disabled Playwright page against the served docs (`page.goto(DOCS_BASE_URL/docs/components/<name>)`, `packages/shadcn/tests/helpers/hydration-invariant.ts` `captureServerElements`), so without a running docs server every one of its component tests fails with `net::ERR_CONNECTION_REFUSED` — an environmental failure, not a regression (verified 2026-09-21: 139/139 failures across 10 test files were ERR_CONNECTION_REFUSED with nothing listening on :3000). Behavior tests use `waitUntil: "networkidle"`, which the dev server's open HMR websocket can keep from ever settling — those timeouts reproduce on `main` and are not caused by component changes. Playwright is resolved from the global homebrew install, not the workspace.

**Calendar demos must pin `defaultFocusedValue`, never rely on wall-clock "today".** `Calendar`'s Zag date-picker machine focuses the browser's real "today" whenever `defaultFocusedValue`/`focusedValue`/`value` is unset, so its rendered day grid (and every `aria-label="Choose <weekday>, <month> <day>, <year>"` on each day button) drifts by one day every day. The fix is a serializable `defaultFocusedValue={ year, month, day }` on the demo source itself under `apps/docs/src/demos/calendar/` (the pattern `calendar-demo.marko`/`calendar-presets.marko` already used), not a Playwright `page.clock` or server-side time freeze. `calendar-min-max.marko` needs no pin: the Zag machine clamps initial focus into the `min`/`max` range on its own. When adding a new Calendar demo (or any date-sensitive component demo), pin its initial date the same way — an unpinned wall-clock date is a regression waiting to happen, not just cosmetic drift.

**After changing any component (`packages/shadcn/ui/**`) or demo (`apps/docs/src/demos/**`) `.marko`/`classes.ts` file, run `bun tooling/build-registry.ts` and THEN `bun run build:demos`, and commit the regenerated `apps/docs/src/demos/demos-manifest.ts` (and any regenerated `routes/docs/components/<name>/` or `tags/docs/demo-renderers/` files) in the same change.** The manifest embeds component and demo source, so it goes stale on any such edit, and CI's `registry-drift` job fails on it ("Generated demos manifest is stale"). This held even when full verification moved to CI (2026-09-28): a dev that runs only its own package's tests still has to run the generators for the files it changed. Missed once on `main` (075d69e3, the calendar caption fix), which turned CI red right after a push. **Order matters:** `apps/docs/scripts/build-demos-manifest.ts` reads the BUILT registry JSON (`apps/docs/public/r/**`, gitignored), not the component source, so `build:demos` alone against a stale `public/r` regenerates a manifest that still embeds the old component code and looks plausible. That happened on the first attempt to fix the red CI (35a42b7b), which left CI red a second time.

**The axe-core WCAG scan (CI job `axe`) runs against a PRODUCTION docs build, not the dev server.** Reproduce it locally using `scripts/ci/serve-docs.sh` (which handles the build and serves on port 3000), then run the scan. Wrap in `flock` to avoid heavy parallel jobs:

```bash
flock /tmp/marko-ui-heavy.lock bash -c 'bash scripts/ci/serve-docs.sh && bun scripts/ci/axe-scan.ts axe-results.json; kill -9 $(lsof -t -i:3000) || true'
```

It scans `/docs/components/<name>` for every `DOCUMENTED_COMPONENTS` entry, scoped strictly to the hero `[data-slot="preview"]` stage (excluding the docs code-peek). It runs two passes: one in the default closed state, and one in an open state for components with overlays or expandable sections. The open state logic is driven by the map in `scripts/ci/axe-open-states.ts` (`OPEN_STATES` configures the trigger and content selectors; `NO_OPEN_STATE` lists components with no openable overlay).

If you add a new component, you must add it to either `OPEN_STATES` or `NO_OPEN_STATE` in `scripts/ci/axe-open-states.ts`, or the scan will fail its completeness assertion.

The scan exits non-zero on **any** violation — there is no baseline or threshold file, and none should be added: 0 means 0. Keep the full `axe-results.json`; its `perPage` map is what makes a failure diagnosable (aggregate it by rule, then by target, before touching any component).

**Local counts run LOWER than CI's — the same violations, not a different set.** The 2026-09-16 fix measured 166 violations locally (162 `scrollable-region-focusable` + 4 `heading-order`, 39 pages) against CI's 241 (237 + 4, 52 pages) on the same 85 pages. CI is a strict superset: headless-Linux font metrics render text wider, so more containers overflow and trip the same rule at the same selectors. Never read a lower local number as "CI was exaggerating" — reproduce, fix by container/markup rather than by chasing a count, and confirm the fix holds at several viewport widths.

**The scoped include does NOT mean every violation belongs to the component.** `[data-slot="component-preview"]` wraps the docs stage *and* the collapsed source peek, so docs chrome is inside the scan scope: of those violations, every `scrollable-region-focusable` node was on the docs code-peek `<pre>` or the fixed-height `h-72` demo stage — zero on any `packages/shadcn` component. They were real defects (genuinely overflowing, no `tabindex`, no focusable children, so keyboard users could not scroll to the clipped content), fixed in `component-preview.marko`/`code-block.marko` with a bare `tabindex="0"`, which adds a focus ring only on focus and changes nothing at rest. When a scrollable container legitimately clips content, make it keyboard-reachable; never silence the rule.

**Make a scroll container focusable with `tabindex="0"` alone — do not add `role="region"` + `aria-label`.** The bare tab stop satisfies `scrollable-region-focusable` on its own (verified on table/dropdown-menu/toggle-group). Naming them instead turns every preview into a landmark, and a docs page renders ~6 previews, ~6 peeks and ~8 code blocks — roughly 20 identically-named landmarks per page for a screen-reader user to page through. The rule wants keyboard reachability, not landmark structure.

**`heading-order` is NOT a page-scope rule — fix the heading instead of disabling it.** It was briefly added to `PAGE_SCOPE_RULES` on 2026-09-16 on the theory that no heading level could be right both standalone and nested; that was **wrong** and was reverted the same day. The real defect was at the page level: in `routes/docs/components/$name/+page.marko` the hero `<component-preview>` was the only section with no heading of its own (Installation/Usage/Examples each open with a visible `<h2>`), so the page jumped straight from the `<h1>` into whatever heading a demo rendered. The fix is a `<h2 class="sr-only">Example</h2>` labelling the hero, after which the demo headings sit at `<h3>` beneath it — the offenders (separator, scroll-area ×2, collapsible ×2) were `<h4>`, and their Tailwind classes pin font-size/weight/leading/margins, so retagging changes heading semantics and nothing visual (the separator hero screenshot is byte-identical before and after). That sr-only `<h2>` **must stay inside a `<section>`**: the behavior suite's `demoByTitle()` helper locates a demo as "the `<div>` whose direct child is a heading", so a bare `<h2>` under the page's outer wrapper `<div>` makes that wrapper match too and every demo lookup resolves to ~29 elements (Playwright strict-mode violation, 52 behavior tests down at once — hit on PR #38). Accordion needs no component change under this scheme: its items are `<h3>` **hardcoded** at `packages/shadcn/ui/accordion/accordion.marko` (matching upstream shadcn's `AccordionHeader`, not Zag-generated), which is correct once the hero sits under an `<h2>`. Before adding any rule to `PAGE_SCOPE_RULES`, prove it reads out-of-scope context (run the scoped scan, then re-run with out-of-scope context removed) **and** that no markup fix exists; never blanket-disable to get green, and never add `aria-hidden` to interactive elements or delete demo content to silence a rule.

## CI path filtering (`.github/workflows/ci.yml`, added 2026-09-16, branch `chore/ci-path-filters`)

`ci.yml` has a `changes` job (using `dorny/paths-filter`, pinned to the v4.0.3 tag's commit SHA `ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d`, never a mutable tag ref) that computes three filters — `cli`, `docs`, `registry` — and every real job is gated on the matching one via a job-level `if:`. This exists purely to skip expensive jobs (`tests`/`axe` build+serve the full production docs bundle, ~2-4 min) on a PR that provably cannot affect them, e.g. a `TODO.md`-only change.

**The filters apply to `pull_request` runs ONLY.** Every gated job's condition reads `github.event_name != 'pull_request' || needs.changes.outputs.<x> == 'true'` — a `push` to `main` (or `workflow_dispatch`) always runs every job unconditionally, regardless of what changed, so main's badges and status stay trustworthy. Don't "simplify" that condition to just the filter output; that would silently start skipping jobs on `main` too.

Job → filter mapping (each filter's actual source-of-truth, not a guess — verified by reading what each job's commands import/build, plus the config files those tools themselves load, such as tsconfig `extends` chains and the root vitest config; the latter class was found in a round-2 pass, not the initial one, so re-derive this list rather than trusting it blindly whenever a job's commands or tooling change):
- `cli-tests` gated on `cli`: `packages/marko-ui/**` (the CLI's own source and tests, run via its own vitest config), plus `bun.lock`/`package.json`/`scripts/ci/**`/the workflow file/`.github/actions/setup/**` as always-relevant infra. `packages/marko-ui/tsconfig.json` does not extend the root `tsconfig.json` (standalone `compilerOptions`), and `cli-tests` never typechecks anyway (`bun run --filter marko-ui test` is vitest-only), so root `tsconfig.json` is correctly absent from `cli`.
- `tests` (behavior/hydration) and `axe` gated on `docs`: both run `scripts/ci/serve-docs.sh`, which builds the registry (`packages/shadcn/**` is the component source, `packages/marko-ui/**` feeds `VISUAL_STYLES`/registry constants) and then `apps/docs` production build (`apps/docs/**`) — plus `tooling/**` (the registry/style build scripts themselves) and the same always-relevant infra as above. `tests` also runs `bunx vitest run` with no `--config`, i.e. the root `vitest.config.ts` (its `include` covers `packages/**/*.test.ts` and `apps/docs/scripts/**/*.test.ts`, and it registers the marko Vite plugin) — added to `docs`. Root `tsconfig.json` is extended by `apps/docs/tsconfig.json` and `tooling/tsconfig.json` — added to `docs` too.
- `registry-drift` gated on `registry`: rebuilds the registry and every committed generated artifact, then fails on any drift. Its inputs are `tooling/build-registry.ts`'s actual imports — `packages/shadcn/**` (the component/style source it transforms), `packages/marko-ui/src/registry/**` (visual style definitions + the registry item schema type), `apps/docs/src/data/directory.json`, and `tooling/**` itself (the transform scripts) — plus `apps/docs/src/demos/**` (input to `build:demos`) and `apps/docs/src/lib/blocks-list.ts` (input to `build:blocks-manifest`), both added 2026-09-21 (branch `chore/ci-hygiene`, issue #48): without them a demo/blocks-list change could silently ship a stale generated artifact while the gate never fired. Root `tsconfig.json` is extended by `tooling/tsconfig.json` — added to `registry` too. `scripts/ci/**` is deliberately NOT in this filter (unlike `cli`/`docs`): `registry-drift` only runs the generators + `git diff`, never anything under `scripts/ci/**`.
  The drift check diffs a **committed manifest, not the gitignored output** (the old `git diff --exit-code -- apps/docs/public/r/` could never fail — `.gitignore:7` hides that tree; issue #40): `tooling/build-registry.ts` writes `apps/docs/registry-manifest.json` (path + sha256 per emitted `public/r/**` file, sorted, with `REGISTRY_BASE_URL` occurrences replaced by a placeholder before hashing so the build-time base URL can never change the hash — the output itself stays gitignored because it embeds that URL). The job runs `git diff --exit-code` on the manifest plus the committed outputs of `build:demos` (`apps/docs/src/demos/demos-manifest.ts` plus the two generated trees `apps/docs/src/routes/docs/components/<name>/+page.marko` and `apps/docs/src/tags/docs/demo-renderers/<name>.marko` — the latter two ALSO gated with `git status --porcelain`, because plain `git diff` misses newly-untracked stale outputs), `build:blocks-manifest` (`apps/docs/src/lib/blocks-manifest.ts`), and `extract:api` (`apps/docs/src/lib/api-reference.json`). All four generators were verified deterministic (two consecutive runs byte-identical) before being gated; if one ever becomes nondeterministic it must be ungated and documented, not absorbed into a tolerance.

Other root-level config surfaces were checked and found not to apply to any of these three jobs: there is no `biome.json`, `.eslintrc*`, or committed prettier config in this repo (`prettier` is a devDependency with no CI script invoking it); there is no `playwright.config.ts` (`test:e2e`'s `playwright test` isn't run by `ci.yml` at all); `e2e/**` only feeds `test:acceptance` (`e2e/acceptance/vitest.config.ts`), which lives in the separate `acceptance.yml` workflow, not `ci.yml`. See the comment block directly above the `changes` job's filter definitions in `ci.yml` for the same list kept in sync with the workflow itself.

**To force a full, unfiltered run on a PR** (e.g. to double-check a change you believe is unrelated, or when in doubt): use `workflow_dispatch` from the Actions tab (or `gh workflow run ci.yml --ref <branch>`). An empty commit does NOT work as a substitute: path filters diff changed paths, and an empty commit changes no paths, so every filter still evaluates false and every gated job still skips. `workflow_dispatch` isn't a fallback for when that fails — it's the correct mechanism from the start, because it runs as its own event type and is never subject to the `pull_request`-only gating condition above, regardless of what paths (if any) changed.

**`ci-ok`** is an always-run (`if: always()`) aggregate job that `needs:` `changes`/`cli-tests`/`registry-drift`/`tests`/`axe` and fails if any of them resulted in `failure` or `cancelled` (a `skipped` result from one of the four gated jobs, driven by the path filter, is treated as fine). `changes` itself is included in that check because it has no `if:` gating it — if it fails outright (checkout failure, action download failure, malformed filter syntax), every job gated on `needs.changes.outputs.*` reports `skipped` rather than `failure`, and without `changes` in the loop, `ci-ok` would read that as "all legitimately skipped" and report a false green on a pipeline that never actually ran. The result-checking step passes each job's result through `env:` and references it in the shell as `$VARNAME`, rather than interpolating `${{ needs.*.result }}` directly into the `run:` script body, to avoid that injection-prone pattern. Branch protection on `main` currently has **no required status checks configured at all** (`gh api repos/svallory/marko-ui/branches/main/protection` → 404 "Branch not protected"), so nothing depends on `ci-ok` today — it's there so that if/when required checks are ever turned on, there's one stable, always-present job name to point at, instead of pointing at jobs that can each legitimately show "skipped" (which GitHub's required-checks UI cannot distinguish from "still queued" without an aggregate).

`publish-badges` (needs `tests`+`axe`, `if: always() && github.ref == 'refs/heads/main'`) needed no changes: it only ever fires on a push to `main`, where the filters are never consulted, so `tests`/`axe` always ran and its `needs:` are satisfied exactly as before.

**One new nondeterminism source was found while stabilizing `chrome-visual.spec.ts`, and fixed with a wait, not a mask: the horizontal `ScrollArea` scrollbar thumb both `blocks-nav.marko` (`/blocks`) and `charts-nav.marko` (`/charts`) use for their category rail.** Both pages carry this — an earlier draft of this note wrongly said only `/blocks` did; `/docs/components/button` is the one page in this spec with no `ScrollArea` at all. `packages/shadcn/ui/scroll-area/scroll-area.marko`'s `[data-slot="scroll-area-scrollbar"]`/`[data-slot="scroll-area-thumb"]` are always DOM-present (by design — see that file's own comment on why, to avoid an SSR/hydration part-count mismatch) and get their geometry from `@zag-js/scroll-area`'s `trackContentResize` effect: a `ResizeObserver` that fires **once at mount** (not per-frame) on the content/root elements, debounced through a 1ms `setTimeout` before dispatching `thumb.measure`, which sets reactive `thumbSize` state (consumed by `<zag>`'s api getter and re-rendered by Marko as the thumb's width/height) and separately writes `thumbXEl.style.transform` directly (`@zag-js/scroll-area@1.43.3`'s `scroll-area.machine.ts`, `setThumbSize`/`trackContentResize`). **Fixed by waiting for the thumb to settle, the same way the accordion case was actually fixed (by removing the source of the race, not by masking around it) — `waitForScrollAreaThumbsSettled()` in `e2e/visual-helpers.ts`, called from `waitForHydration()`.** It polls every `[data-slot="scroll-area-thumb"]`'s computed `transform`/`width`/`height` for 3 identical consecutive frames (the same signature `waitForLayoutSettled` uses for the whole page), so it waits exactly as long as the machine's debounced measurement actually takes and no longer, and still fails loudly rather than racing if a thumb never stops moving. Verified: 3 local runs with the wait in place and **no mask** — `chrome-visual.spec.ts`'s `masksFor()` returns `[]` — all 12 baselines byte-identical across all 3 runs, including `blocks-light-mobile`, the specific case that flaked before the fix.

**`.github/workflows/visual.yml`'s four baseline-handling steps (existence preflight, pre-regenerate delete, oxipng optimize, commit) are generalized over every spec the `visual` Playwright project actually runs, not hardcoded to `gallery-visual.spec.ts`.** This matters because a hardcoded single-file path here is not just untidy — it is a silent coverage hole: a new visual spec (like `chrome-visual.spec.ts`) added without updating a hardcoded preflight would have no baselines, and Playwright's own "write missing baseline, exit 0" behavior would make that spec's guard pass green while asserting nothing, exactly the failure mode the preflight step exists to catch.

**Baselines are Linux-only and are generated ON THE RUNNER — never locally.** macOS and Linux disagree on font rasterisation, so a darwin baseline can never match a CI run. `playwright.config.ts` gives this spec its own `visual` project whose `snapshotPathTemplate` puts `{platform}` **back** (the repo-wide template strips it, which is right for DOM-text snapshots and wrong for PNGs), so a stray darwin baseline is never silently compared against a linux run. **Threshold is `maxDiffPixels: 0`, justified by measurement — do not raise it to silence a red run.** Verified: 3 consecutive full-matrix runs, 49/49 passing, plus a separate harness that hashed 3 independent browser launches of the same page to byte-identical SHA-256. **What is frozen vs. masked, and why.** Frozen with injected CSS (preferred — the component still renders and is still asserted): animations/transitions paused at their final frame, caret colour, focus rings. The **accordion** needs a special case: its open/close animates to a height a `ResizeObserver` measures at runtime (`--marko-accordion-content-height`, see `packages/shadcn/styles/marko-accordion.css`), and the callback can land on either side of a capture — measured as a real ~2,900-pixel diff between two runs of the same commit, so the spec kills the accordion's `animation`/`transition` (landing the panel on its natural height) and waits two `requestAnimationFrame`s after hydration. **Do NOT pin `height: var(--marko-accordion-content-height)` on open panels — that was the fix here until 2026-09-17 and it was actively wrong** (see the entry below). Masked (only where JS writes geometry every frame, so CSS cannot freeze it): the "Audio Frequency Visualizer" card (`Math.sin(Date.now()) + Math.random()` bar heights via `requestAnimationFrame`), the marquee, and the "Seats Held" `[data-slot="timer"]` (an `autoStart` countdown rewriting `--value` once a second). Masks cover the smallest possible region — the timer element, not its card — so surrounding card chrome, which is what the style layers actually change, stays under test. **Freeze before you mask, and never fix nondeterminism by editing a demo**: the demos are what ships.

**Never feed `--marko-accordion-content-height` back in as a height on anything the ResizeObserver measures — that was a real component bug, not a test-harness gap (root-caused 2026-09-17, branch `fix/visual-flake-lyra`, issue #45).** The var is the observer's **output**: `accordion.marko`'s `publishHeight` writes `el.scrollHeight` of the `[data-slot="accordion-content"]` panel into it, and the `marko-accordion-down`/`-up` keyframes are its only legitimate consumer. Two places were also using it as an *input* height, in both cases closing a feedback loop where the measurement's output became the input to the thing being measured:

1. `packages/shadcn/ui/accordion/classes.ts`'s `contentInner` carried `h-(--marko-accordion-content-height)`. Once a value was published, the inner div was locked to it, so the panel's `scrollHeight` reported that stale number instead of the content's real height and the observer could never correct itself. Upstream shadcn's inner div is `pt-0 pb-4` with **no height at all**, so this was never parity — removing it is both the fix and a return to parity.
2. `e2e/gallery-visual.spec.ts`'s freeze CSS pinned `height: var(--marko-accordion-content-height)` on open panels, re-creating the same loop from the test side and freezing whichever value happened to be measured first.

**Why it presented as lyra-only, and why "only one style" is the diagnostic signature here.** Each style layer gives `.mu-accordion-content` different type metrics, so each has a genuinely different correct panel height — measured on `/create/preview?item=preview-page-1`: **lyra 74px** (`text-xs`, 12px/16px), nova 90px (`text-sm`, 14px/20px), mira 94px, the other five 116px. The spec loads the page under the app's default style (nova) and *then* swaps the `style-*` class, so the first measurement is always nova's 90px. For nova that value is right; for lyra it is 16px too tall, and with either loop in place the observer can never republish. So it is not that lyra has an extra animation or transition — grep confirms `style-lyra.css` has no accordion animation the other 7 lack; it is that lyra's correct height differs most from the default's, and the stale value was being frozen. **A visual-guard failure on exactly one style, with a pixel count identical across runs, means a value measured under a DIFFERENT style got frozen — not that the style itself is nondeterministic.**

Evidence it is a production bug and not only a test artifact: with `classes.ts` fixed and no freeze CSS at all, swapping nova to lyra makes the panel resize 90px to 74px and the observer republish `74px`; before the fix it stayed at 90px indefinitely. Any reflow that changes the content's natural height but not the panel's box — a style switch through the `/create` customizer, a late font load, longer i18n text — hit the same stuck height, with `overflow: hidden` on the panel. Verified after the fix: the open animation still ramps 0 to the style's own height (0→70px nova, 0→58px lyra, smooth intermediate frames), no clipping, single-select close still works, `packages/shadcn` mtc stayed 0.

Local stability, `preview-page-1`, real spec freeze CSS extracted from source, full-page captures compared by decoded pixels (macOS, so baselines can't be compared — only run-to-run stability): **lyra light 20/20 byte-identical, published height 74px in all 20**; with the pin still in, also 20/20 identical but stuck at the wrong 90px — i.e. **run-to-run stability alone does not prove the height is right, so assert the published value too, per style.** Full 8-style × light/dark matrix, 4 runs each: **16/16 cells stable**, each at its own correct height.

**Removing the loop moved ALL 16 `preview-page-1` baselines, not just lyra's 2 — and the cause of the other 14 is NOT established.** On the runner, each of the 16 diffs is a **pure vertical translation confined to the accordion card**: unchanged glyphs, everything below the open panel shifted up by 1–4px (nova ~20px), no reflow and no new clipping (verified by decoding both baseline versions and comparing raw pixel buffers, then checking row alignment after shifting — 92–100% match for most styles). That is the full extent of what is measured. **Do not repeat the "integer-rounding slack" explanation an earlier version of this note asserted: it was measured false.** On macOS, all 8 styles show `scrollHeight` exactly equal to the panel's fractional `getBoundingClientRect().height` (slack **0.0**, not the ~1.1px claimed), and re-applying the old inner-div pin on nova reproduces **no shift at all**. The one `88.90625` reading behind that claim was a panel measured pre-swap mid-hydration, before its height settled — a transient, not a steady state. So the mechanism for the 14 non-lyra shifts remains open; if it matters, investigate on a Linux runner, where the shift actually reproduces.

Two things that *are* established and worth knowing: the pre-fix `preview-page-1-luma-*` baselines had the open panel's last text line **clipped mid-glyph** (the `overflow: hidden` symptom — a committed baseline was asserting the bug as correct), and `preview-page-2`/`preview-page-3` are untouched because neither page renders an accordion. Practical consequence: a change to this component's box model is expected to move every style's baseline at once, so a **one**-style move is the suspicious case, per the diagnostic signature above.

**Never wait for layout with a fixed `waitForTimeout` — use `waitForLayoutSettled()`.** The style swap rewrites radius/padding/border/font-weight, the page reflows, and the accordion's `ResizeObserver` then republishes its measured height off the back of that reflow. A fixed 250ms sleep was a bet that all of it finishes in time: it held on a developer laptop and **lost on the CI runner**, producing a 4,102-pixel diff on exactly one cell of the matrix (`preview-page-1 — mira dark`) while a 24-sample probe found the *settled* page perfectly stable — the signature of a settling race, not ongoing churn. The helper instead samples document scroll size plus every element's bounding box on `raf` polling and requires **three identical consecutive frames**, bounded by a 20s timeout so a genuinely animating page fails rather than hangs. It terminates despite the masked animators because those change *pixels*, not *box geometry* — a future mask on something that reflows would need different handling.

**`reducedMotion: "reduce"` is set on the `visual` project, so anything gated on `prefers-reduced-motion` baselines in its DEGRADED form.** Nothing on the three preview pages currently reads that media query, so today this changes nothing. But if a reduced-motion-gated style (a `.shimmer`, a skeleton pulse, a parallax) is ever added to a preview page, its baseline will capture the reduced variant and the guard will never see the motion path. That is the right default for a screenshot guard — the alternative is capturing whatever frame an animation happened to be on — just don't mistake a green run for "the animated form is verified".

**Baselines are losslessly optimized before they are committed, and that is safe because Playwright compares decoded pixels, not file bytes.** The update job runs `oxipng -o 4 --strip safe` over the regenerated PNGs, then re-runs the comparison to prove the optimization changed nothing, before committing. Measured on the runner (the `du -sk` figures the step prints): **11644KB → 8600KB, a 26% reduction**, with all 48 files byte-**different** and all 48 **decoded-pixel-identical** (verified by hashing `PNG.sync.read().data`), and a full comparison run green afterwards. `oxipng` is downloaded from **its own GitHub release, pinned to an exact version and verified against a recorded SHA-256** before it runs — this job holds `contents: write`, so an unverified binary is not acceptable. Two other routes were tried and rejected: the `oxipng` **npm** package is an unofficial third-party repackage (`mvasilkov/oxipng`, stuck at 1.0.1, last published over a year ago), and **apt has no `oxipng` on the `ubuntu-24.04` runner** at all — `E: Unable to locate package oxipng`, confirmed by a failed CI run, despite `packages.ubuntu.com/noble/oxipng` returning a soft-200 page that looks like it exists. When bumping the version, update the SHA-256 alongside it or the step fails closed. **Never substitute a lossy optimizer** (`pngquant` and friends): it would alter pixels and silently rewrite what the guard asserts.

**A new nondeterministic demo will show up as a flaky style/page that moves between runs.** Don't bump the threshold. Diff two captures to get the changing bounding box, map it to an element, and decide freeze-vs-mask — that is how all four sources above were found.

## Architecture: the SSR-safe Zag pattern

Marko 6 is resumable: the server serializes reactive state and the client never re-runs render. Zag services and `connect()` APIs contain functions and are **unserializable**, so they must never be reactive state or cross a tag boundary as raw values — only template-written **closures** (getters) are serializable currency. Every interactive component follows the same shape (see `packages/marko-ui/README.md` for the full example):

1. Server renders full aria/data attributes from a never-started machine (a throwaway instance `<zag>` reads before mount).
2. Client builds its own service in `onMount`; `<zag>` returns the **api getter**, whose identity changes on every machine notify and on every tracked props change — no hand-written `rev` counter or dependency list.
3. Call the getter at every use site (`api().getRootProps()`); `<const>` recomputes automatically because the getter it reads is `!==` the previous one.

Registry components express this via marko-zag's `<zag>` tag (`packages/shadcn`'s single authored source, one line: `<zag/api=() => mod from=input/>`), which picks the machine's props out of `input`, generates an `id`, applies a default `on<X>Change` → Marko `xChange` sugar rule, creates and connects the service, and returns the api getter — collapsing the old three-tag `<machine-props>`/`<service>`/`<connect>` wiring (and the `rev`/`ServiceHandle` plumbing it needed) into one line. A component that needs the running service itself (to thread into a child, or connect a second module against it — see `toast/toast.marko`, `menubar/menu.marko`) uses `<zag-machine>` plus a plain `connect()` call instead; `<zag-machine>` returns a **service getter** (`service()`), never the raw service. Controlled props re-notify automatically: `<zag>`/`<zag-machine>` track whatever the `props=` closure reads.

`normalizeProps` is Marko-specific: `class`/`for` renames, style-object hyphenation, `event.currentTarget` shadowing (Marko delegates events), SSR handler stripping. `<zag>`/`connect()` apply it by default, so most components never import it.

## Registry structure rules

- One authored component source (`packages/shadcn/ui/`), not one full implementation per style. Components carry semantic `mu-*` hook classes; the 8 shadcn styles live as vendored CSS token layers in `packages/shadcn/styles/style-<name>.css`, shipped as SOURCE (not precompiled). Per-style flat components for the copy path are produced IN MEMORY by `tooling/build-registry.ts` via a data swap: each component's `classes.ts` (pure data, per notes/component-authoring.md) is resolved against a style's CSS by `tooling/resolve-classes.ts`, then `tooling/merge-classes.ts` injects the resolved literal (`static const styles = {...} as const;`) into the single copy-path file's part, replacing its `./classes.ts` import — there is no on-disk `styles-gen/`. Class strings never live in `.marko`/`variants.ts`; `tooling/check-classes.ts` enforces it. See `notes/style-ports.md` and `notes/plans/dual-distribution-plan.md` for the full architecture and its history.
- **Last synced to upstream shadcn 98a1fe6 on 2026-09-28 (styles + bases/base).** `tooling/parity/harnesses/shadcn/upstream-shadcn.ts`'s `ensureShadcnClone` has no pin mechanism — it always tracks upstream's tip — so this line is the only record of how current the 8 style layers and the `bases/base` component port are. Update it whenever a sync lands; see `notes/style-ports.md` for the sync log and method.
- `packages/shadcn/package.json` `exports` lists `./ui/*`, `./lib/*`, `./styles/*`, `./blocks/*` pointing directly at the real authored files — no generated indirection.
- Compound components use attr-tags with a **single tag name + `type` discriminant** when order matters — cross-name attr-tag order is unrecoverable in Marko. `items=` arrays remain as sugar. Docs: `/docs/creating-components` §5 and `notes/component-authoring.md`.

## Docs-app CSS (imports the shipped theme, 2026-09-26)

## The docs site's own canonical URL

`apps/docs/src/lib/site-meta.ts` exports `SITE_URL` — the single source of truth for the docs site's own public URL (canonical links, OG/Twitter tags, the homepage's self-referential QR-code demo, the typeset Get Code drawer's `absoluteUrl()`). It reads `import.meta.env.VITE_SITE_URL`, falling back to `https://marko-ui.saulo.tech`.

**The env var is `VITE_SITE_URL`, not `SITE_URL`** — deliberately, not a typo. This app's `vite.config.ts` has no `envPrefix` override, so Vite only exposes `VITE_`-prefixed variables through `import.meta.env`; a bare `SITE_URL` would silently resolve to `undefined` at every call site and the fallback would always win, with no error to signal the misconfiguration. `import.meta.env` (not `process.env`) is required for the same reason `lib/component-page-data.ts`'s `REGISTRY_BASE_URL` stays a plain literal instead of reading `process.env`: `site-meta.ts` is imported by client-bundled code (the typeset Get Code drawer, via `tags/typeset/lib/docs-content.ts`), and `process` is not defined in that bundle — `import.meta.env.VITE_SITE_URL` is what Vite statically inlines for both the server and client builds.

Registry/CLI install-command URLs (`https://marko-ui.saulo.tech/r/...` in `card-install.marko`, `block-viewer.marko`, the `/docs/cli`, `/docs/theming`, `/docs/components-json` route pages, `data/directory.json`, and `lib/component-page-data.ts`'s `REGISTRY_BASE_URL`) are a **different concern** — the registry endpoint, not the site's own identity — and are deliberately left as literals, mirroring the CLI's own `REGISTRY_URL` env-with-fallback pattern in `packages/marko-ui/src/registry/constants.ts`. Don't route these through `SITE_URL`.

## Dual distribution and the `mu-*` public styling API

There are two shipping paths, not one: **copy** (`marko-ui add` copies per-style flat generated source, transformed in memory at build time — classes are baked flat, "the code is mine now") and **import** (the `@marko-ui/shadcn` package, which ships the `mu-*` hook-class components plus the 8 style layers **as source**, for the consumer's own Tailwind to compile). For the import path, `mu-*` hooks are a **public styling API**: consumers override or switch styles from their own stylesheet. Full mechanics — the `layer(components)` requirement and the `@custom-variant` shipping requirement — are documented in `notes/css-architecture.md`.

## Testing the CLI against a real scaffold

The CLI's vitest suite never runs `init`/`add` against a real project, so a
whole class of first-run defect is invisible to it — the CLI's own tests all
pass while `bunx marko-ui init` hangs, crashes, or leaves the user with a
project whose CSS never loads. Every one of the 2026-09-17 first-run fixes was
found this way and none was catchable in-repo.

```bash
bun run test:cli:e2e
```

That builds the CLI, builds and serves the registry locally, scaffolds a
throwaway `create-marko` app, and drives `init` / `add` / `build` through it.
`e2e/cli/first-run.sh` holds the assertions; `e2e/cli/run.sh` is the wrapper.
It runs in CI as a step of the `cli-tests` job (gated on the `cli` path filter,
~36s locally).

**Assert on the build output, not on files and flags.** This is the trap that
made the first version of this harness worthless: it checked that `init` wrote
the stylesheet and set the tsconfig flag, all of which passed, while the built
CSS was 776 bytes with no theme tokens and no component utilities in it. A
`create-marko` scaffold imports no CSS anywhere (its layout uses an inline
`<style>`) and has no Vite config, so writing a stylesheet does not make it
load. The decisive assertions are that a component utility (`inline-flex`), a
theme token, and the `mu-font-heading` hook rule all appear in `dist/**/*.css`,
and that the emitted CSS asset is actually referenced by the built output.

`iconLibrary` in `components.json` is honored at add time by
`packages/marko-ui/src/utils/icon-library.ts` (`applyIconLibrary`, called from
`updateFiles` and the dry-run/diff path): it keeps only the configured library's
`__<lib>__.ts` map, drops `client-swap.ts` and `icon-mapping.json`, and replaces
`resolve.ts` with a single-library resolver. If you change `resolve.ts`'s
exports in `packages/shadcn/ui/icon/`, update `renderIconResolver` to match
(a unit test runs it against the real maps). The e2e asserts the built output
of a scaffold per library contains only that library's icon data. The import
distribution (`@marko-ui/shadcn`) is unaffected: all five libraries, lucide default.

`bun run test:cli:e2e` drives ONE project shape in ONE order. The scenario
suite, `bun run test:cli:scenarios` (`e2e/cli/scenarios/`, plan and defect list
in `notes/cli-test-plan.md`), builds many shapes from small hand-made fixtures
(monorepos, no tsconfig, jsconfig, existing Tailwind, every lockfile) and runs
the built CLI through the orderings and environments users hit. Package
managers/runners are logging shims, skills come from `MARKO_UI_SKILLS_SOURCE`,
never GitHub. A scenario the CLI fails today is `{ fails: "Dn" }` (`it.fails`):
the suite is green until a fix lands, then RED until the mark is removed —
remove the mark, never weaken the assertion. `SCENARIOS_SHOW_FAILURES=1` shows
the real failure behind each mark. Prefer a scenario here for orderings,
structures and environments.

Other traps, each of which cost a debugging cycle:

- **The registry must be built AND served locally.** `tooling/build-registry.ts`
  changes (dependencies, file targets) only exist in local output, and the CLI
  otherwise fetches the live registry, which this document notes is stale
  relative to `main`. Registry items also embed absolute URLs, so the build
  needs `REGISTRY_BASE_URL` pointing at the local server.
- **Ports 4447-4460 are bound by the CLI unit suite.** `src/registry/resolver.test.ts`
  listens on 4447-4449 and 4455-4460, so a registry server left running on any of
  them makes `bun run test:cli` fail with `EADDRINUSE` in a file unrelated to the
  change. `test:cli:e2e` serves on 4455 (it must not overlap a unit run);
  `test:cli:scenarios` defaults to 4470, which nothing binds. `run.sh` refuses to start
  on a port already in use and always stops its own server; override with
  `REGISTRY_PORT`.
- **Run the CLI with stdin closed** (`< /dev/null`) and a timeout. That is what
  a CI/agent caller looks like, and it is what surfaces a prompt nothing can
  answer — the failure mode is a hang, so without a timeout the harness hangs
  too.
- **Drive interactive behavior under a real pty, with a window size.** Stdin
  closed only proves the non-interactive path; `init`'s questions (base color,
  distribution, visual style) only exist on a TTY, and `-y, --yes` once
  defaulted to `true`, so a real terminal silently took defaults while every
  test passed. `expect(1)` spawns a pty whose size is 0x0 unless you
  `set stty_init "rows 40 columns 120"` first; at 0 columns `ora` erases
  lines forever (millions of cursor-up sequences, then a stall on pty
  back-pressure) and it reads as a hang in `init`. `init.test.ts` has a
  pty-driven suite that does this; unset `CLAUDECODE`/`CI`/`CURSOR_AGENT`/
  `REPL_ID`/`AI_AGENT` for the child or the CLI correctly refuses to prompt.
- **Idempotence needs a real second run.** Hash the project tree, run `init`
  again, compare. Several first-run defects only appear on the second call.

## Acceptance suite (published packages, live registry)

`e2e/acceptance/` tests the **published** `marko-ui`/`@marko-ui/shadcn` npm packages and the **live** registry deploy (`https://marko-ui.saulo.tech/r`) — not the workspace. It exists to catch a broken publish or a stale registry deploy in CI before a user hits it. Run with `bun run test:acceptance` (own vitest config, not part of `bun run test`/`bun run check` — see `.github/workflows/acceptance.yml`, `workflow_dispatch` + weekly cron, deliberately not in `ci.yml` since it depends on external services).

Covers four journeys, each scaffolding a real app in its own temp dir outside the repo:

- **copy path** (`copy-path.test.ts`) — `bun create marko`, wire Tailwind v4 by hand (the installation page assumes it exists but doesn't scaffold it), `marko-ui init`, `marko-ui add button switch card`, `bun run build`, assert the rendered output actually contains the component markup.
- **add + doctor/diff** (`add-doctor-diff.test.ts`) — add a zag-machine component (switch) and a composite (dropdown-menu), `marko-ui doctor` (expect pass), `marko-ui diff` (expect no drift right after add).
- **import path** (`import-path.test.ts`) — `bun add @marko-ui/shadcn marko-zag`, wire the CSS entry per `packages/shadcn/README.md`, build, assert `mu-*` hook classes are present (the import path's public styling API — copy-path output has flat utility classes + `data-slot` instead).
- **registry health** (`registry-health.test.ts`) — fetch `index.json` + component JSONs from the live registry, schema-validate against the CLI's own `registryItemSchema`, and check a stable marker: every zag-machine component's source uses the current single `<zag/api=... from=input/>` tag, not the retired `<machine-props>`/`<service>`/`<connect>` three-tag wiring.

Env vars (all optional, sane defaults): `ACCEPTANCE_REGISTRY_URL` (default the live registry), `ACCEPTANCE_PKG_VERSION` (default `latest`) — retarget at a staging registry or pre-release tag without touching test code. `ACCEPTANCE_KEEP_TEMP=1` keeps the scaffolded temp app dirs instead of deleting them, for debugging a failure.

**A CLI symlink-resolution defect this suite found (2026-09-08) is FIXED on `main`** (PR #16, `12f5448c`): `packages/marko-ui/src/index.ts`'s entrypoint guard compared `import.meta.url` (Node resolves it through filesystem symlinks) against an unresolved `pathToFileURL(process.argv[1])`. On macOS, `os.tmpdir()` returns a `/var/folders/...` path and `/var` is itself a symlink to `/private/var` — invoking the CLI with that unresolved path made the comparison silently fail: `main()` was never called, the process exited 0, and **nothing was printed or written, no error, no exception**. `main` now canonicalizes `argv[1]` with `realpathSync` before the comparison (falling back to the raw path if it can't be resolved), with a regression test (`packages/marko-ui/tests/entrypoint-symlink.test.ts`) invoking the built CLI through a symlinked path. This is fixed only in source — **any published version at or before `marko-ui@0.2.0` on npm still has the bug**, so a caller targeting an older/pinned version (via `ACCEPTANCE_PKG_VERSION`, or any consumer pinned to `0.2.0`) can still hit it. `e2e/acceptance/lib/workspace.ts` keeps realpath'ing its temp workspace before handing any path to the CLI regardless, since the suite must work against both old and new published versions.

**A real, confirmed gap in the live registry deploy, found by this suite (2026-09-08):** every zag-machine component (`switch`, `checkbox`, `tabs`, `dropdown-menu`, etc.) served by `https://marko-ui.saulo.tech/r` still carries the retired `<machine-props>`/`<service>`/`<connect>` three-tag wiring, not the current single `<zag/api=... from=input/>` tag — even though `main` and the published `@marko-ui/shadcn@0.2.0` npm package both have the current source. The copy-path `marko-ui add switch` therefore fetches source that fails to build (`Unable to find entry point for <machine-props>`). The import path is unaffected (it resolves from npm, not the HTTP registry). This means the Coolify registry deploy is stale relative to `main`/npm — see `add-doctor-diff.test.ts` and `registry-health.test.ts` for the reproducing assertions, and `report-acceptance.md` for the full writeup.

**That staleness should be gone once the Cloudflare cutover lands, and the reason is structural, not a one-off re-deploy.** The registry is now built and published by `.github/workflows/pages.yml` on every push to `main`, from `main`'s own source, so the served registry cannot drift from the branch the way a manually-triggered container deploy could. Re-run `bun run test:acceptance` against the live URL after the cutover to confirm, and only then treat this entry as historical — the assertions in `registry-health.test.ts` are what settle it, not the deploy log.

**Badge denominators must be able to express failure.** The hydration badge
used to divide by "number of hydration tests that ran", which on a green run
always equals the number that passed — so it published "33/33 identical" and
was read as full coverage while 21 components had no test at all. A badge
whose denominator is the work you chose to do cannot report a gap. Divide by
the real population — the APPLICABLE set (`ZAG_BACKED_COMPONENT_COUNT` minus
`NON_INVARIANT_BY_DESIGN`, not the raw population: an exception like `tour`
can never demonstrate the invariant, so counting it would paint a permanent
"53/54" and train readers to ignore a real gap) — and prefer yellow over
green when coverage is partial.

**Badges are audience-split across two branches (2026-09-21, branch
`feat/release-pinned-badges`).** The site home is for consumers and must
describe the last PUBLISHED release, so it reads the `badges` branch, which
`.github/workflows/release.yml` rewrites from the release tag (after pushing
`v<version>`) by running the full badge pipeline on the tagged tree.
`badges-main` is main's numbers, fed by ci.yml + lighthouse.yml on every
push to main; the README reads that. Both are orphan branches written by
`scripts/ci/publish-badges.sh <dir> [branch]` (default `badges`), whose
fetch→reset→add-files→commit→push-with-retry makes concurrent publishers to
the SAME branch safe — a publisher never rewrites another branch's files
because each run starts from that branch's remote state and adds only its
own.

**Behavior coverage (#72) badge: only stubs-free lists count.**
`coverage.json` (`<pct>% · <listed>/<all> components`) is generated from
`bun scripts/ci/behavior-coverage.ts --json` by ci.yml's `tests` job (published
to `badges-main`, README) and by release.yml's release-badges job on the tag
(published to the release-pinned `badges` branch; skipped for tags whose
badge.ts predates the kind, v0.4.0 and older). The site home shows the
release-pinned badge as a separate coverage card.
Its build-time loader (`apps/docs/src/lib/coverage-badge.ts`) fetches raw GitHub
with a timeout and retries transient errors; a short timeout reproduced the
missing card in a local static crawl even though the badge was available. Pages
checks `dist/public/index.html` for the card before deploying, so a missing or
malformed badge cannot silently ship a green deployment. Local/offline builds
may still omit it with a logged cause; never hardcode a fallback percentage or
read `badges-main` for consumer-facing coverage. The percentage is covered /
*reviewed* behaviors of the listed components — a `behaviors.ts` entry with
`status: "stub"` (from `scripts/ci/scaffold-behaviors.ts`) is excluded from
every count until reviewed. Details in `notes/behavior-coverage.md`.

**A badge is only as trustworthy as the job that publishes it.** `Publish
badges` failed on every push to main from 2026-09-12 to 2026-09-17 because
`combine` still required the removed style-matrix job's artifact, so the
badges on the README silently went stale while CI showed red. When removing a
CI job, grep for every consumer of its artifacts.

## Deploying (Cloudflare Worker with static assets)

**`apps/docs` is a fully prerendered static site plus one small Worker, deployed to Cloudflare as a Worker with static assets — NOT classic Pages, and no longer the Coolify Node server.** The distinction matters for cost and for how you reason about a bug: asset requests are free and unlimited and never run any code, and the Worker is invoked only for the two paths in `assets.run_worker_first`. Config is `apps/docs/wrangler.jsonc` (project `marko-ui-docs`); `DEPLOY.md` has the full operational detail.

```bash
bun run --cwd apps/docs build     # dist/public (static) + dist/worker/index.js
bun run --cwd apps/docs deploy    # wrangler deploy
```

CI does this on every push to `main` via `.github/workflows/pages.yml`, which builds the registry with the production `REGISTRY_BASE_URL`, builds the site, **asserts the output is complete** (a crawl that silently drops pages still exits 0 — the step checks for `404.html`, `_headers`, the prerendered handler outputs, the per-item preview documents, ≥120 registry JSONs and ≥165 HTML pages), then deploys with a SHA-pinned `cloudflare/wrangler-action`.

**Client chunk policy lives in `apps/docs/vite.config.ts` as Rolldown `codeSplitting.groups`, not a `manualChunks` function, and the first group pins Vite's `\0vite/preload-helper.js` to its own ~1.3 KB chunk (#81).** Any dynamic `import()` reachable from a route's client graph pulls that helper; under `manualChunks` Rolldown co-located it inside the ~770 KB shiki bundle, so a single lazy import in a shared component added ~268 KB gzip to every route that did not already load shiki (measured: `/create` 371 KB to 639 KB, `/` 409 KB to 678 KB). `advancedChunks` is the deprecated spelling of `codeSplitting` (Vite warns). `scripts/ci/check-preload-helper.ts` (a step of CI's `tests` job, after `check:html`) inspects the built chunks and fails if the chunk holding the helper also holds shiki or exceeds 50 KB. Routes that legitimately load shiki (the docs component pages, `/typeset`, via the code highlighter) are unaffected either way.

**The zag stack is split per machine (#87): `vendor-zag-<machine>` chunks plus one `vendor-zag-core` (marko-zag, every non-machine `@zag-js/*`, and zag's third-party deps), named by `apps/docs/vendor-chunks.ts`.** The former single `vendor-zag` group was 815 KB raw and every route downloaded it. The machine list is derived from `packages/shadcn/package.json`, so a new machine dependency gets its own chunk automatically. Two traps, both hit while building it: (1) the group must set `includeDependenciesRecursively: false` — the default drags each machine's dependency tree into that machine's chunk, so unrelated machines end up importing (say) angle-slider's chunk for `dom-query`; (2) with it off, any third-party dependency of a zag package that no group claims (`uqr`, `@internationalized/number`, ...) lands in an app chunk and creates a machine-chunk to app-chunk cycle, which overflows the stack in `@marko/run`'s post-build walk (`RangeError: Maximum call stack size exceeded` in `marko-run-vite:post closeBundle`). Add such a dependency to `THIRD_PARTY_OWNER`. `scripts/ci/check-no-duplicate-modules.ts` (a module in two chunks of one build) and `scripts/ci/check-route-budgets.ts` (`scripts/ci/route-budgets.json`, gzip first-load bytes = measurement + 5%; raise deliberately with `--update`) guard the built output. Built chunk FILE NAMES are not reproducible between builds of the same tree — on `origin/main` too (see the #87 report) — so do not assume cross-deploy cache stability from the vendor names.

**The build is a crawl, so a page only ships if something points at it.** `@marko/run-adapter-static` seeds only PARAMETERLESS routes and then follows anchor links; every dynamic route (`$name`, `$category`, `$type`, `$item`) is invisible to it unless listed in `staticUrls()` in `apps/docs/vite.config.ts`. That function derives its URLs from the same modules the pages read (`COMPONENTS`, `BLOCK_CATEGORIES`, `CHART_TYPES`, the typeset `FIXTURES`, `PREVIEW_ITEMS`), so adding a component prerenders it automatically — **keep it that way rather than hardcoding a list**, or a new component will 404 in production while every test passes. A healthy build logs `Crawled 346, success 337, failed 0`; the 9 "not found" are pre-existing dead links in docs content (`/docs/primitives/*`, `/docs/typeset`), not regressions.

**`staticUrls()` must never return a path already covered by a parameterless route, and must never return duplicates (fixed 2026-09-28, branch `fix/static-crawl-dupes`).** `@marko/run-adapter-static@2.0.10`'s `crawl()` builds `pathsToVisit` from every parameterless route in `routes.list` PLUS whatever `staticUrls()` returns, with no dedup pass — it maps the whole (possibly duplicated) list straight into concurrent `visit()` calls under `Promise.all`. Each `visit()` opens `fs.createWriteStream(filePath)` for its own path; two concurrent visits of the same path both write the same file at once, and whichever write finishes second "wins", but the loser's write can still leave trailing bytes behind — this corrupted `apps/docs/dist/public/docs/components/chart.html` intermittently (duplicated `</script></body></html>` tail, ~3 of 4 builds), since nearly every component already has its own generated static route (`src/routes/docs/components/<name>/+page.marko`) and `staticUrls()` was pushing `/docs/components/<name>` again for all of them, unconditionally. The adapter passes `routes.list` into `staticUrls(routes)` for exactly this purpose — filter against `route.path.path` for every route with no `path.params`, and dedupe the returned array (a `Set` is the simplest way) as a safety net. Verify a fix to this function with two separate `bun run build` runs (never `--update-snapshots`, and never on port 3000 — see the crawl/dev-server traps elsewhere in this doc) each followed by `bun run check:html`; a corrupted `chart.html` fails `check:html`'s close-order validation, not silently.

**The crawler silently drops a non-HTML response at an extensionless path.** Its `visit()` writes a non-HTML 200 only when the path matches `/\.\w+$/`; otherwise it aborts and writes nothing. `/docs/components/<name>.md` is therefore written directly, but `/typeset/css` and `/docs/components/<name>/md` are not — `apps/docs/scripts/prerender-handlers.ts` imports and calls those real handler modules (never a reimplementation) and writes each body to the literal extensionless path. That shape is forced: Cloudflare matches non-HTML assets by EXACT pathname, and its index resolution (`/folder` → `/folder/index.html`) is for `.html` only, so there is no `index.css`/`index.md` to lean on. Because those files have no extension, they get no inferred `Content-Type` — `public/_headers` declares it, and **deleting those two rules would serve the CSS and the markdown as unknown-type downloads.**

**`/create/preview` cannot be a single static file, and this is the subtle one.** The page picks its entire body from `?item=` at RENDER time, and a static host cannot vary a file by query string (`_redirects` matches on path only — its `source` is a file path, verified against the Cloudflare docs). Left alone, all three items would collapse onto one document and **32 of the 48 gallery baselines would silently become screenshots of preview-page-1 while the guard still passed.** So each item is prerendered as its own document via `routes/create/preview/$item/+page.marko` (which imports the parent page rather than copying it, so the two can never drift), and the Worker rewrites `?item=` onto it — keeping the public URL the customizer iframe and `e2e/gallery-visual.spec.ts` both use. The parent page reads the item from the PATHNAME, not `$global.params`: it is typed against its own parameterless route, so `params` is `{}` there even when the request arrives through the `$item` route.

**The Worker deliberately does not use `@marko/run/router`.** Re-exporting it (what the default server entry does) pulls in the whole route table, hence all 86 component pages and every Zag machine: measured 7.28 MB raw / 1.31 MB gzipped, over the Workers size limit, to serve one route. `apps/docs/worker/entry.ts` imports only `+layout.marko` and the single `+page.marko` and renders them with Marko's template API, giving 2.37 MB raw / **530 kB gzipped**. The POST response therefore comes from the genuine templates, not hand-written HTML that would drift from the page. Validation rules live in `src/lib/no-js-form-schema.ts` and are imported by BOTH the route handler and the Worker — there is one definition of the rules, which is what keeps the "forms validate without JavaScript" claim honest.

**`scripts/ci/serve-docs.sh` runs `wrangler dev --local`, not a static file server.** The suites must run against what ships, and the pieces only the Worker provides are exactly the pieces they exercise: the `/no-js-form` POST (`packages/shadcn/tests/behavior/no-js-form.test.ts`) and the `/create/preview?item=` rewrite (the visual guard). A static-only server would 404 the POST and serve the wrong preview page.

**Running the whole vitest suite in parallel against one local wrangler produces false failures.** 14 `waitUntil: "networkidle"` timeouts came out of a parallel run whose files are fine: a direct probe of the URL that timed out at 30 s settles networkidle in ~1.7 s, and `--no-file-parallelism` gives 274/274. Use `--no-file-parallelism` locally before believing a timeout is a regression.

**A local `wrangler deploy` can fail with a bare `TypeError: fetch failed` that has nothing to do with Cloudflare.** If `HTTPS_PROXY`/`NODE_EXTRA_CA_CERTS` are set (a corporate or agent-sandbox proxy), wrangler's undici dispatcher does not pick up the proxy CA and every API call fails — including its own metrics post — while plain `curl` and plain Node `fetch` to the same host succeed. The tell is that the failure hits the FIRST request (`GET .../workers/services/<name>`), before any upload. Deploy with `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy wrangler deploy`. CI is unaffected.

**Bare component pages (`/bare/<name>`) exist solely as Lighthouse targets.** The docs layout includes a 2MB site-wide CSS bundle and docs-specific chrome that invalidates component-level performance/SEO measurement. A separate Vite build step (`marko-run build -c vite.bare.config.ts`) emits chrome-free pages containing ONLY the component's default demo and its active style CSS, deployed alongside the main docs. They are the Lighthouse bare-pages target — see the "Lighthouse on bare pages" row in the Public numbers table for the current scores and derivation; never restate the score from prose. The main docs pages (`/docs/components/*`) remain the axe and behavior-test targets. To test locally: build and serve with `bash scripts/ci/serve-docs.sh`, then run `bunx @lhci/cli autorun --collect.url="http://localhost:3000/bare/<name>"` (configure presets in `.github/lighthouse/lighthouserc-bare-*.json`).

**Package & HTML Validity Gates (2026-09-17)**
New gates were added to ensure the credibility of the output. The package integrity gate (`bun run check:pkg`) runs `publint` and `attw` during CI (`pkg-checks` job) and before npm publishing.
